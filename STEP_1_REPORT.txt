F. Browser Buyurtmalarim=0 trace
Browser UI requests `GET /api/orders`. Backend identifies the user via JWT (`type: 'auth'`) and queries `orders` where `auth_user_id = public.users.id`. However, the Telegram Mini App order creation path (`POST /api/orders`) only saves `telegram_id` to the order row, leaving `auth_user_id` NULL. Thus, the database query returns 0 rows for the browser session.

G. Receipt upload trace
Frontend sends `payment: "Karta (Uzcard / Humo)"`. Backend saves this exact string. The frontend calls `POST /api/orders/.../receipt`. `paymentReceiptFinalRuntime.js` intercepts it and explicitly checks `if (order.payment !== 'card_manual')`. The check fails (returns 400). The frontend catches the error and silently attempts a non-existent `/api/customer/orders/.../receipt` fallback, finally showing "Failed to fetch".

H. Telegram admin notification trace
`telegramAdminBotProduction.js` uses a continuous `while(true) poll(); sync();` loop. It deduplicates notifications using an in-memory `Map` (`state.sigs`). If Render scales out to 2 instances during a deployment, both instances run the loop, both lack the memory state for a new order, and both send the album to Telegram admins concurrently.

I. Payment state trace
Because receipt uploads fail the hardcoded `"card_manual"` check, the payment state remains stuck in `pending`. Legacy systems parsing the raw string `"Karta (Uzcard / Humo)"` may default to "Naqd" visual representations.
